## Ordered writes and recovery state

The schema migration stages only the coverage objects. It keeps a bounded transaction-local `statement_timeout` for DDL, installs the source-write and delete-capture triggers, validates every inventory table has a non-null uniquely ordered UUID `id`, and initializes one private progress row per inventory table. It does not scan or project historical source rows. This removes the prior four-minute all-rows transaction that exceeded the temporary login lifetime.

The worker invokes `prospect_candidate_private.coverage_backfill_batch(text,uuid,integer)` for one allowlisted source table at a time. Every call accepts at most 100 rows, orders by UUID, locks selected source rows, projects them, and stores the cumulative count, last UUID and completion flag in the same transaction. `SET LOCAL statement_timeout='60s'` bounds each call and disappears when that transaction ends. `coverage_backfill_status()` exposes counts, cursors and completion only. Both functions and the progress table are private and inaccessible to application roles. Insert/update triggers project concurrent changes; a `BEFORE DELETE` trigger projects `OLD`, so a deletion cannot disappear while the keyset scan is catching up.

The protected worker acquires a temporary CLI credential only after the second review and refreshes it as it approaches expiry. It checks durable status at startup and after every attempted batch. If the command response is lost, it queries status before deciding what to do: an advanced checkpoint means continue at the next cursor; an unchanged checkpoint means the atomic batch did not commit and may be retried. Repeated no-progress failures reduce the batch size (100, then half) and fail closed if even a one-row batch cannot proceed. The worker never treats its own process receipt as completion proof. Any uncertain run leaves `started_unverified` plus a marker and can resume only by reading the database checkpoint.

After all inventory tables report complete, the workflow obtains a separate credential for independent read-back. That read-back verifies the ledger prefix ten, exact source statements, complete-source contract, installed triggers/RPCs, every backfill completion flag and an empty coverage-only dry-run. It records aggregate counts and the verified receipt before changing coverage to `verified`. If a failure occurs, the profile-link migration is skipped. A new protected run reconciles the real ledger and database cursors, then resumes only the incomplete batches. It never reapplies the coverage migration after prefix ten.

The final migration can start only when the local state says coverage is verified. It must then verify the exact eleven-migration release prefix, an empty pending plan, complete source/ledger agreement and the candidate-complete gate. A failure or read-back mismatch leaves the phase `started_unverified`, emits a recovery marker, exits nonzero, and uses GitHub's default step-success dependency so later writes do not run. If a writer or read-back fails, do not replay coverage. Dispatch a new protected recovery only when its read-only preflight proves the exact prefix-ten state with matching coverage ledger statements, catalog objects, and the final migration as the sole dry-run item. That run skips the coverage writer and performs read-back before it can reach the final migration. Any other state fails closed for manual investigation.
