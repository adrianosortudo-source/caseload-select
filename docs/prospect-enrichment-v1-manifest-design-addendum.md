# Prospect enrichment v1 manifest design addendum

The v1 data/API plan specifies seven core storage tables. Migration `20260923161812_prospect_enrichment_v1.sql` retains those seven and adds two run-manifest tables: `prospect_enrichment_run_manifest_chunks` and `prospect_enrichment_run_manifest_items`. This is a deliberate schema extension: the system must account for every candidate in a research run, including held or malformed candidates that never become package rows.

A JSONB manifest array on the run row would make large manifests difficult to page and reconcile, and would not give each submitted chunk and expected candidate an independently append-only identity. The two normalized tables provide bounded, retry-safe registration and a durable read model without changing package review, apply, or verification states.

- `prospect_enrichment_run_manifest_chunks` stores one immutable receipt per `(run_id, chunk_index)`, including the exact chunk body, hash, and entry count. Exact retries are idempotent; a different body at the same index conflicts. Finalization requires the declared contiguous chunk range and the reconstructed manifest hash. Each request is bounded to 2 MiB and 1,000 entries; the producer normally emits smaller chunks.
- `prospect_enrichment_run_manifest_items` stores one immutable row per expected manifest entry, including source provenance, error codes, initial disposition, and the expected package/item lineage when a package exists. A package-less hold has a null `client_package_id` and payload hash, zero items, and still counts toward the expected run-entry total. Package entries have unique client package IDs and retain their expected research key, payload hash, and client item identities. Keyset reads can return this inventory without loading the full run manifest.

The finalization trigger reconciles packages that were staged before a manifest arrived. Every staged package must have one manifest entry with the same client package ID, research key, and payload hash; missing entries and orphans reject finalization. The run-level lock serializes manifest finalization with staging. Once finalized, staging accepts only a package whose expected payload and exact client-item lineage match the inventory.

Run inventory is complete only when the manifest is finalized, received entry and package counts equal their expected counts, and missing-package, payload-mismatch, research-key-mismatch, and orphan-package counts are all zero. Held entries remain visible in run detail even though they have no package. This inventory status proves intake coverage; canonical prospect visibility still requires the separate operator apply receipt and authenticated read-back verification.
